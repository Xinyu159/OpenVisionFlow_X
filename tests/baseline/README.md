# 基线快照

## `upstream_501_type_ids.txt`

上游（`ovf-algorithm/`）那 **501 个算子的 type_id 全名单**，一行一个，字典序。

**干什么用的：** 这份名单是「**一个老算子都不许少**」这条硬约束的**可执行判据**。

之前验收脚本里写的是 `count == 501`。加了用户算子（`ovf-nodes/`）之后，
这个判据就废了 —— 总数变成 502、以后还会变，而**数量的变化恰恰掩盖不了
真正的风险**：某个老算子被顶掉了，同时你的用户算子多了一个，总数照样"正常"。

改成按**名字**做集合包含检查之后，判据与用户算子的多少彻底解耦：

```
上游 501 个 type_id  ⊆  进程注册表里的 type_id
```

这条在 `/tmp/e2e_verify.py`（Web 端 e2e）里跑。**阶段 8 应该把它收进 CTest**，
别让它只活在 `/tmp` 里的脚本中。

**怎么来的：** 阶段 4 开工**之前**，用当时那份（阶段 3 的）`ovf-web-server`
跑 `GET /api/nodes` 抓下来的 —— 那时候注册表里还只有上游 501 个，
是干净快照。

**什么时候该改：** **永远不该改。** 这份文件是上游的指纹。
上游算子被删除/改名是硬约束禁止的事；真发生了一定是有意的决定，
那时候要显式更新这个文件，并在 `docs/hardening/` 里写清楚为什么。
